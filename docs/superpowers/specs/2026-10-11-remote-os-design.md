# Remote OS — WebRTC desktop sessions on the agent box

Owner brief (11 Oct 2026, condensed from the "Master Engineering Prompt"): a Chrome-Remote-Desktop-class, browser-based remote desktop on ONE cloud VM — persistent real-time WebRTC streaming (never screenshot polling), H.264, low input latency, bounded queues, measured FPS/latency/bitrate, isolated sessions with an explicit lifecycle, a Rust supervisor, and a viewer in the admin. Targets are measured, never claimed.

## Decisions taken with the owner
- **Scope: personal, done properly.** One owner (the existing admin allow-list), several isolated desktop SESSIONS (e.g. per org/project), not a multi-tenant SaaS. No PostgreSQL: session metadata in SQLite on the box (the spec's tables, minus multi-user quota machinery). Auth = the same Firebase ID token + allow-list agentd already verifies.
- **Display: X11 (Xvfb) first, honestly labelled X11; native Wayland is Milestone 2.** Verified on the box: Weston is 8.0 and has no virtual-input protocol; the wlroots compositors that do (sway/cage/labwc) are not packaged for Oracle Linux 9 and must be built from source. Capture and input sit behind `CaptureBackend` / `InputBackend` traits so Wayland drops in later.
- **Media path: TURN over TCP 443** (coturn on the VM). The Cloudflare tunnel carries HTTP/WebSocket only, so signalling rides the tunnel and media rides TURN. coturn relays ONLY to this box (deny all peers, allow its own private address), short-lived credentials via `use-auth-secret`, never an open relay.

## Verified box facts (Oracle A1, 4× Neoverse-N1, OL9.8)
- No GPU encoder (`/dev/dri/card0` is the virtio display): **software H.264 only**.
- Packaged: GStreamer 1.22.12 base/good/bad-free (but NOT the webrtc plugin — built from source with libnice 0.1.22, see the spike report), libnice 0.1.19 (EPEL, too old for webrtcbin), coturn 4.18 (EPEL), PipeWire 1.4, Rust/cargo 1.92, ffmpeg-free 7.1 (codeready_builder needed). NOT packaged: x264, OpenH264 plugin, sway/wlroots.
- Today's baseline to beat (measured 10 Oct): MJPEG push over the tunnel at 800×450 — idle ≈ 1 frame/5 s, motion ≈ 5 fps at ≈ 28 KB/frame (≈ 1.1 Mbit/s); input via xdotool spawn per action.

## Milestone 1 (this build)
Rust workspace `remote-os/` (supervisor = Axum + Tokio + gstreamer-rs `webrtcbin`): one session end to end — Xvfb+XFCE session as its own unprivileged unix user under a systemd scope with CPU/memory/pids limits, `ximagesrc → videoconvert → x264enc (zerolatency, no B-frames, bounded queues) → webrtcbin`, signalling over an authenticated WebSocket through the tunnel, a reliable ordered DataChannel for input (versioned typed protocol, sequence numbers, size/rate limits, release-all on disconnect), XTest input in-process (no xdotool spawn), TURN credentials minted per connection, keyframe on request, three profiles (720p30 / 1080p30 / 1080p60), adaptive bitrate. Viewer in the admin (native `<video>`, WebRTC stats overlay: fps, bitrate, RTT, jitter, packet loss, decode time). Benchmarks recorded in `remote-os/IMPLEMENTATION_STATUS.md` against the MJPEG baseline.

## Milestone 1 contract (both builders code against THIS)
Spike results: `remote-os/benchmarks/2026-10-11-encode-spike.md`. Consequences: each session's Xvfb runs AT the profile resolution (no in-pipeline scaling — scaling cost ~45% of a core), x264 `tune=zerolatency speed-preset=ultrafast bframes=0`, quality mode with a bitrate cap and `qpmin≈20` (idle 0.65–1 Mbit/s instead of 1.7–2.4), keyframe on PLI/FIR, `profile-level-id` pinned to `42c02a` (L4.2) for 1080p60. Cap 3 concurrent sessions; 1080p60 only alone. `GST_PLUGIN_PATH=/usr/local/lib64/gstreamer-1.0` must be in the unit (webrtcbin, libnice 0.1.22 and x264enc are built from source into /usr/local).

**Hosts.** Signalling `https://desk.ravikishan.me` → tunnel → supervisor `127.0.0.1:7780`. Media: TURN `turn:92.4.83.196:443?transport=tcp` (coturn, relays only to 10.0.0.118); the browser uses `iceTransportPolicy: "relay"`; webrtcbin's host candidate on 10.0.0.118 is reached by coturn. TURN credentials: coturn `use-auth-secret` — username `<unix-expiry>:<session-id>`, credential `base64(HMAC-SHA1(secret, username))`, TTL 10 min; secret at `/etc/remote-os/turn.secret` (root:coturn 640 — the supervisor user gets read via group).

**Auth.** Firebase ID token (RS256, Google x509 certs, `aud=iss=myportifilio-3ab5f`, `email_verified`, email in `AGENT_ADMIN_EMAILS`) — the same rule agentd uses. REST: `Authorization: Bearer <idToken>`. WS: first message `{type:"auth", token}` within 5 s or close 4401.

**REST** (JSON, `/api/v1`): `GET /health` (no auth) · `GET /sessions` · `POST /sessions {name, profile:"720p30"|"1080p30"|"1080p60"}` (idempotency key header `Idempotency-Key`) → `{id, name, profile, state, width, height, fps, createdAt}` · `GET /sessions/:id` · `POST /sessions/:id/stop` · `GET /sessions/:id/stats` · `GET /capacity`. States: CREATING READY CONNECTED IDLE STOPPING STOPPED FAILED. Errors `{error, code}` with codes `capacity/full`, `session/not-found`, `profile/unknown`, `auth/*`.

**Signalling WS** `GET /api/v1/sessions/:id/signal` → after auth the server sends `{type:"ice-servers", iceServers:[...], policy:"relay"}`; client sends `{type:"ready"}`; server builds the pipeline and sends `{type:"offer", sdp}`; client answers `{type:"answer", sdp}`; both trickle `{type:"ice", candidate, sdpMLineIndex}`; `{type:"bye"}` either way. One viewer per session at a time (a new one replaces the old, which gets `{type:"replaced"}`).

**DataChannel `input`** (created by the server, ordered + reliable). Client → server JSON, `v:1`, monotonically increasing `seq`, ≤ 512 bytes, ≤ 400 msgs/s:
`{v,seq,t:"pm",x,y}` pointer move, x/y normalised 0..1 of the video's content box · `{v,seq,t:"pd"|"pu",b:1|2|3,x,y}` button down/up · `{v,seq,t:"wh",dx,dy}` wheel (notches) · `{v,seq,t:"kd"|"ku",code,key}` KeyboardEvent.code + key → mapped to X keysym server-side · `{v,seq,t:"rel"}` release all held keys/buttons · `{v,seq,t:"hb"}` heartbeat every 2 s · `{v,seq,t:"clip",text}` set remote clipboard (≤ 64 KB, own message size limit) · `{v,seq,t:"res",profile}` request a profile change. Server tracks held keys/buttons and issues release-all on channel close, heartbeat loss (6 s) or `rel`. Server → client on channel `status` (unordered ok): `{t:"stats", fps, bitrate, encodeMs, width, height, captured, encoded, dropped}` every 1 s and `{t:"clip",text}` when the remote clipboard changes (owner-initiated pull via `{t:"clip?"}`).

**Browser access (added by the viewer builder, 11 Oct — the viewer calls the supervisor CROSS-ORIGIN from the admin, so these are required, not optional).**
- **CORS on every `/api/v1` REST route.** Echo the request `Origin` in `Access-Control-Allow-Origin` only when it is exactly one of `https://www.ravikishan.me`, `https://ravikishan.me`, `http://localhost:3000` (never `*`), with `Vary: Origin`. Preflight `OPTIONS` answers 204 WITHOUT auth: `Access-Control-Allow-Methods: GET, POST, OPTIONS`, `Access-Control-Allow-Headers: Authorization, Content-Type, Idempotency-Key`, `Access-Control-Max-Age: 600`. No cookies are used, so no `Allow-Credentials`. Error responses (401/404/409/5xx) must carry the same CORS headers, or the browser reports every refusal as an opaque network failure and the viewer cannot say what happened.
- **WebSocket `Origin` check.** CORS does not cover a WS upgrade; refuse an upgrade whose `Origin` is not on the same list (HTTP 403, or close 4403).
- **Shapes the viewer reads.** `GET /sessions` → `{sessions:[Session]}` (a bare array is also accepted). Session = the POST shape plus optional `viewer:boolean` (a viewer is attached) and `lastActiveAt`. `GET /capacity` → `{max, running, profiles:{"720p30":{allowed:boolean, reason?}, "1080p30":{…}, "1080p60":{…}}}` where `running` counts sessions not STOPPED/FAILED and `reason` is a sentence (e.g. "1080p60 runs only when it is the only session"). If `profiles` is absent the viewer derives it from `max`/`running` and the 1080p60-alone rule.
- **WS close codes the viewer explains:** 4401 auth (missing/late/invalid token), 4403 not allowed (allow-list or Origin), 4404 session not found / not running, 4409 replaced by another viewer (after `{type:"replaced"}`), 1000 after `bye`. Anything else is treated as a drop and retried (3×, then the viewer stops and says so).
- **ICE messages** carry the candidate as a STRING: `{type:"ice", candidate:"candidate:…", sdpMLineIndex}` (also `sdpMid` if available). The viewer never sends end-of-candidates.
- **Clipboard pull** is `{v,seq,t:"clip?"}` on the `input` channel (same seq space); the reply is `{t:"clip",text}` on `status`. **Profile change** `{t:"res",profile}`: when applied the server MAY send `{t:"res",profile,width,height,fps}` on `status`; the viewer otherwise relies on the decoded resolution changing. A refused input/res MAY be answered `{t:"error",code,error}` on `status`, shown verbatim.
- **Client-side limits** the viewer already applies (so the server's are a backstop): pointer moves coalesced to one per animation frame, ≤ 250 msgs/s total, discrete events never dropped (queued, bounded at 256 — overflow sends `rel` and clears), messages > 512 bytes refused before sending (`clip` ≤ 64 KB), `hb` every 2 s while the channel is open, `rel` on window blur, `visibilitychange` → hidden, `pagehide`, Drive → Watch, disconnect and channel close. Browser-reserved shortcuts (Ctrl/Cmd+W/T/N/Q, Ctrl+Tab, Ctrl+Shift+Tab/N/T, Cmd+H/M, F11) are never sent. Driving is gated client-side on a sign-in from the last 30 min (Firebase `auth_time`); the supervisor SHOULD additionally refuse input from a connection whose token `auth_time` is older than 30 min, so the gate is not client-only.

**Supervisor as built (added by the supervisor builder, 11 Oct — additive; nothing above was removed).**
- **Implemented as specified:** every REST route, the WS sequence, both server-created channels (`input` ordered+reliable, `status` unordered with `maxRetransmits:0`), CORS exactly as in "Browser access" (preflight 204 without auth, headers on every response including errors, `Vary: Origin`, never `*`), WS `Origin` check (HTTP 403 before upgrade, so the browser sees close 1006, not 4403 — a refused upgrade cannot carry a close code). A WS request with NO `Origin` (not a browser) is allowed; the token still decides.
- **Shapes:** `GET /sessions` → `{sessions:[Session]}`; Session carries `viewer:boolean`, `lastActiveAt` (last state change, RFC 3339) and, when FAILED/STOPPED by the system, `error`. `GET /capacity` → `{max, running, profiles:{id:{allowed, reason?}}}`. `GET /sessions/:id/stats` → `{session, viewer, stream}` where `stream` is the last status-channel stats object or null. Error codes in use: `auth/missing|malformed|unknown-key|invalid|expired|unverified-email|forbidden|keys-unavailable|origin|timeout|stale-sign-in`, `capacity/full`, `session/not-found|state|unit-failed`, `profile/unknown|needs-restart|rate-limited`, `idempotency/mismatch` (422: same key, different body), `request/invalid`, `media/failed`, `signal/*`, `clip/unavailable`, `turn/unavailable`.
- **POST /sessions** waits up to 15 s for the display (typically ~0.3 s) and returns `READY` with 201; an `Idempotency-Key` replay returns the same session with 200 for 24 h (keys are per account).
- **Close codes:** 4401 (no/late/invalid/expired token), 4403 (allow-list refusal), 4404 (unknown session OR not running), 4409 after `{type:"replaced"}`, **1000 after `{type:"bye", reason:"session stopped"}`** when the session is stopped or its desktop unit dies.
- **Re-auth:** the client may send `{type:"auth", token}` again at any time; a socket whose token expired more than 30 s ago is closed 4401.
- **Driving needs a recent sign-in (server side):** input frames from a connection whose token `auth_time` is older than 30 min are dropped (counted in `rejected`) and the server sends `{t:"error", code:"auth/stale-sign-in", error}` on `status` once. Sending a fresh `auth` restores it.
- **Profile change `{t:"res"}`:** Xvfb 1.20 cannot resize (one RandR mode), so a change that alters the size (720p ↔ 1080p) is refused `{t:"error", code:"profile/needs-restart"}` — make a new session. A frame-rate-only change (1080p30 ↔ 1080p60, capacity permitting) is applied: `status` gets `{t:"res",profile,width,height,fps}`, then the WS gets **`{type:"renegotiate", profile, width, height, fps}`** — the client discards its RTCPeerConnection, creates a new one and sends `{type:"ready"}` again; a fresh offer follows. One `res` per 3 s.
- **Status stats** units: `bitrate` bit/s; `encodeMs` mean per frame over the last second; `captured/encoded/dropped` cumulative since the pipeline started. Extra fields: `bitrateCapKbps` (adaptive VBV cap), `keyframes`, `rejected`, `rttMs`, `loss`, `profile`.
- **Server ICE** messages carry `candidate` + `sdpMLineIndex` (no `sdpMid`); `ice` from the client with `candidate:null`/empty is ignored. `ice-servers` holds one TURN entry (`turn:92.4.83.196:443?transport=tcp`, 10-min HMAC credentials); if the TURN secret is unreadable the list is empty and a `{type:"error", code:"turn/unavailable"}` precedes it.
- **Keyframe sizing:** x264 runs `pass=qual quantizer=23 qpmin=20`, VBV cap = profile bitrate, **VBV buffer ≤ 150 ms and ≤ ~90 KB per frame** (1080p60 → 102 ms; measured: 500 ms let keyframes burst into coturn's TCP leg and lost ~20 % of them, which froze the picture behind PLIs; 150 ms → 0 loss). The offer carries **NACK + RTX** (`do-nack`), so congestion loss is repaired by retransmission rather than a keyframe.
